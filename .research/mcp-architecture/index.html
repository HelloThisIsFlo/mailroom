Mailroom MCP Architecture

dual-identity design — automated triage backend + interactive email access for Claude
README.md · decisions.md

01 The "Two Front Doors" Concept

Mailroom gains a dual identity: it remains an automated triage backend (the polling service) while also becoming an interactive email access layer for Claude via MCP. Both identities share the same foundation — clients, config, credentials — but serve fundamentally different purposes.

Existing

Polling Service

Automated email triage via SSE push + interval polling.
Runs as a long-lived daemon.
Uses ScreenerWorkflow for triage logic.
mailroom run
New

MCP Server

Interactive email access via Claude tool calls.
Runs as a stdio subprocess.
Uses JMAPClient directly — no workflow.
mailroom mcp

02 Side-by-Side Comparison

Two interfaces, one infrastructure. The polling service automates; the MCP server assists.

Dimension Polling Service MCP Server
Trigger SSE events / timer interval Claude tool calls
Entry point mailroom run mailroom mcp
Process model Long-running daemon stdio subprocess
Logic layer ScreenerWorkflow mcp/tools.py (direct client calls)
Clients used JMAPClient + CardDAVClient JMAPClient only (Phase 1)
Purpose Automated triage (move, label, contact) Interactive access (search, read, label)
Side effects Contact creation, group membership, label reconciliation across all mailboxes Only what Claude explicitly requests
Concurrency Single-threaded poll loop + SSE thread Serial (stdio, one request at a time)

07 Key Design Decisions

Each card summarizes a decision. Click to expand full rationale. See decisions.md for the complete tradeoff analysis.

DEC-01
Monorepo
Single package, single venv, single test suite
The MCP server lives in src/mailroom/mcp/. It imports mailroom.clients.jmap directly. No separate repo, no published library, no path hacks.

Why: The project is ~950 lines. A subdirectory is proportionate.
Revisit when: project grows to multiple maintainers
DEC-02
No Config Split
Same config.yaml + env vars for both identities
Zero new config surface. If you can run mailroom run, you can run mailroom mcp. Same JMAP token, same categories, same mailbox names.
Revisit when: MCP-specific settings emerge
DEC-03
No Workflow Dependency
MCP tools never import from workflows/
Intentional boundary. The workflow embodies policy (conflict detection, retry safety). MCP tools are operations. Exposing poll() as an MCP tool would be dangerous — automated triage from a casual conversation.
Revisit when: never (intentional)
DEC-04
Sync Client in Async Tools
httpx.Client works fine for stdio transport
MCP tools are async def but call JMAPClient synchronously. stdio transport is inherently serial — no concurrent request handling to worry about. Zero refactor to existing code.
Revisit when: migrating to async clients or SSE transport
DEC-05
stdio Transport
Subprocess, no HTTP server, no auth needed
Personal use case. Claude Desktop/Code launches the MCP server as a subprocess. The process inherits the parent's environment. Zero infrastructure.
Revisit when: need remote MCP access
DEC-06
Warm Client via Lifespan
Connect once at startup, store on app context
FastMCP lifespan pattern. JMAPClient.connect() runs once, persists for the server's lifetime. Avoids ~200ms/request for session discovery. Idiomatic for long-lived MCP servers.
Revisit when: never (lifespan is idiomatic)
DEC-07
Logging Strategy
Same structlog, stderr (not stdout)
MCP protocol uses stdout. structlog writes to stderr. No conflict. Same log format regardless of entry point. Claude Desktop captures stderr for debugging.
Revisit when: MCP logging conflicts with stdio
DEC-08
Email-First
Phase 1 = email tools only, contacts later
Fastest path to value. Email search/read/label covers the primary use case. Contact tools come in Phase 2 using existing CardDAVClient. Don't refactor on the critical path.
Revisit when: Phase 1 ships successfully
DEC-09
Raw Body Parts
No HTML-to-text, no MIME parsing in Phase 1
JMAP returns structured body parts. Pass them through. Claude handles both plain text and HTML natively. Keeps initial implementation simple.
Revisit when: user feedback requests rendering
